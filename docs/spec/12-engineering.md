# 12. Engineering

## Code map

| File | Responsibility |
| --- | --- |
| `launcher.py` | Entry point: opens the window, runs the command line, or internal helper modes (`--pk-backup` backup with progress lines, `--pk-encryption` password via stdin, `-m pymobiledevice3`) |

| `.github/workflows/tests.yml` | Runs `tests/run_all.py` on Mac and Windows for every push and pull request |
| `.github/workflows/build-installers.yml` | Builds Mac (Apple Silicon, Intel) and Windows installers; test builds from every pull request |

Talks to the iPhone through **pymobiledevice3** (open source); decrypts backups with **iphone_backup_decrypt**; images with **Pillow** / **pillow-heif**; spreadsheets with **openpyxl**.

## Architecture rules

- **One module per kind of data**, each with a loader (returns plain data) and a writer (saves files). The phone window and exports both use the loader; never parse the same database twice in different places.
- **UI never blocks:** device and backup work runs in background threads; results come back to the UI thread through a queue.
- **Anything that writes to the phone** goes through one module (`phone_write.py`, to create) that performs the confirmation check and the activity log entry. No other module may call a phone write API. In P1 that means three actions: turning on backup encryption (the first-run **Turn on encryption** click is the confirmation; no second dialog), changing the backup password, and turning on Wi-Fi sync (both with a named confirmation dialog). Every dialog names the phone and says exactly what changes.
- **Paths from the phone or a backup** always go through `safe_join` / `safe_local`.
- If the UI is rebuilt in a native toolkit (SwiftUI on Mac, WinUI on Windows), keep the Python core as the engine behind a small local interface; do not rewrite the data code without agreement.

## Tests

- Test scripts live in `tests/` and run on every push and pull request in GitHub Actions through `tests/run_all.py`, on Linux (with a virtual display) to keep the Actions bill small; Mac and Windows runs are started by hand from the Actions tab when a change is platform-specific, and always on a release tag. A failing test blocks the pull request.
- In the repository today: full fake backup of every kind of data; WhatsApp + WhatsApp Business backup; rich photo backup (months, Live Photos, videos, thumbnails); security tests (script injection, path escapes, spreadsheet formulas); phone-window actions with a simulated iPhone (`test_phone_window.py`).
- Every feature adds tests for its **Done when** points that can be automated.
- Keep a library of **anonymised real backups** from several iOS versions for regression tests; never commit real personal data. They are made with the redaction tool (X2, below) and live in a separate private repository, never in this public one.
- Visual checks (screenshots of every screen, light and dark) are generated by a script and attached to pull requests that change the UI. Check them on a real Mac.

### X2. Backup redaction tool

A script, `tools/redact_backup.py`, that makes an anonymised copy of a real backup for the regression library. Rules:

- Runs only on the owner's computer; real backups never leave it. The script lives in this repository; its output never does.
- The copy contains **no photos, videos, voice notes or attachments**: each is replaced by a placeholder file of the same type and size.
- Names, phone numbers, email addresses, postal addresses and all message, note and calendar text are replaced with generated values, consistently (the same real name becomes the same fake name everywhere). The phone's serial number, UDID, phone number and Wi-Fi details are replaced too.
- Prints a report of everything it replaced, by kind and count, so the owner can check a copy before it goes anywhere.
- Approved copies go in a separate private repository.
- Ready before B5, which is the first feature that needs real Finder/iTunes backups.
- How it decides: known databases (Messages, Contacts, Calls, Notes, Calendar, Voicemail, Safari, WhatsApp, Voice Memos, Photos) are copied and rewritten column by column (content columns replaced by kind: name, number, email, address, link, text; structural columns kept, except values shaped like a number, email, id or link); rich-text blobs are dropped; every other file becomes a placeholder of the same type and size (zero-filled); Info.plist and Manifest.plist lose their identifiers; the copy is unencrypted.

**Done when**
- [ ] A redacted copy of a real backup opens in PhoneKeep with every screen populated, and a search of the copy for any name, number or sentence from the original finds nothing.

### Pull requests

Every feature pull request is named with its ID (`B3 Snapshots over time`) and carries:

- a line **Needs:** `Mac only` · `phone by cable` · `phone on Wi-Fi` · `Windows` (any that apply), so on-device checks can be batched;
- a numbered on-device checklist for the owner, designed to take 15 minutes or less, with what to capture (screenshot or recording) for each **Done when** point;
- the **Done when** list with the points provable in CI ticked, and automated tests for them;
- the link to the pull request's "Build installers" run (installers downloadable from it) and the installer sizes from its summary;
- the Status column in [02-roadmap.md](02-roadmap.md) updated;
- a status block at the end: finished · in progress · blocked.

## Build and release

- Version number lives in `phonekeep.py` (`VERSION`), `packaging/PhoneKeep.spec` and `packaging/PhoneKeep.iss`; change all three together, and only in a release pull request ("Release 5.0") that also tags `vX.Y.Z`. Between releases the version stays as it is.
- **Test builds:** installers are built on demand (Actions tab → Build installers → tick the targets; Apple Silicon by default) and on every release tag (all three), not on every pull request, to keep the Actions bill small. A test build is labelled `<next release>-dev+<feature ID>` (next release from `packaging/next-release.txt`, ID from the branch name, e.g. `b3-snapshots` → B3). The label is written into `build_label.py` at build time, and shown in the About box (click the version in the window header) and by `phonekeep-cli --version`, so the build being tested is never in doubt. The installers are downloadable from the run; the run summary lists each installer's size, SHA-256 and whether it was signed.
- Every installer build runs a **launch check**: the packaged app opens its real window, prints `PKLAUNCH ok <version>` and quits. A build whose app doesn't start fails.
- **Build installers** workflow: also runs from the Actions tab or by pushing a tag `vX.Y.Z` (which publishes a GitHub Release with installers and SHA-256 checksums in the notes).
- Releases follow the definition of done in [README.md](README.md) and the checklist in [docs/release.md](../release.md), including the usability test in [00-user-experience.md](00-user-experience.md).

## Command line

Every feature that saves or backs up also works from the command line (`phonekeep-cli`), with the same options as the window, for automation. Existing commands: `devices`, `backups`, `backup`, `run`, `export` (`--only`, `--chats`, `--formats`, `--from`, `--to`), `whatsapp`, `photos`, `encryption on|off`.

## Out of scope (do not build without written agreement)

| Not building | Why |
| --- | --- |
| Installing or downloading apps (.ipa) | Only the App Store may do this |
| Updating or restoring iOS, recovery and DFU modes | High risk of data loss; Apple's own tools do it |
| Company device management (supervision, MDM, configuration profiles) | Different audience |
| Developer tools (location simulation, network capture, system logs, pairing records) | Different audience; adds risk |
| Signed legal-evidence exports and e-discovery formats | Different audience |
| Any cloud service, account or online sync | Conflicts with "data stays on the computer" |
| Reading Signal | Signal keeps its data out of backups |
| "RAM cleaners", speed boosters, battery savers or junk cleaners | iOS manages memory and background activity itself; a computer can't change them, so these would be dishonest (see [13-phone-health.md](13-phone-health.md#ground-rules-for-this-area)) |
| Changing iPhone settings from the computer, or removing profiles or apps from it | iOS doesn't allow it, or it is device management; PhoneKeep shows the steps on the phone instead |
